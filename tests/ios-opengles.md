# OpenGL ES in an iOS app

`ios-opengles.m` uses OpenGL ES as iOS games do. It is run on the Pocket
display, with `tools/pocket-host` standing in for the phone (see
`ios-pocket-display.md`). `OpenGLES.framework` (`src/frameworks/OpenGLES`) is
EAGL on the host's EGL and OpenGL ES: Mesa on Linux, the phone's driver on
Android. An app draws into a renderbuffer it sized to a `CAEAGLLayer`, and
presenting it reads the pixels back into the layer's contents. UIKit draws
those as part of the view.

```sh
gcc -O2 -o pocket-host tools/pocket-host/pocket-host.c tools/pocket-host/pocket-server.c -lz -lpthread
# build ios-opengles.m as ios-pocket-display.m is built, with -framework OpenGLES -framework QuartzCore, and mark it iOS
DARLING=darling tests/ios-opengles.sh ./pocket-host /path/in/prefix/ios-opengles out
```

The host needs `libEGL` and `libGLESv2`. On Mesa, no X server or Wayland
compositor is needed: EAGL uses the surfaceless platform.

The app checks:

- A view's `-layer` is of its `+layerClass` (`CAEAGLLayer`), with the view as
  its delegate.
- An OpenGL ES context (3 if the host has it, else 2) can be made current.
- `-renderbufferStorage:fromDrawable:` sizes the renderbuffer to the view in
  pixels (`contentScaleFactor`), and a framebuffer on it is complete.
- Shaders compile and link. Clearing (red) and a drawn quad (green, the left
  half) read back as those colours, with no GL error.
- A `CADisplayLink` drives presenting: at least 5 frames in 3 seconds.
- ES 3: a `glBlitFramebuffer` from another framebuffer (blue) lands in the
  top right corner. Its last two arguments are on the stack, where Apple's
  arm64 ABI and the host's disagree (see below).
- Presenting makes the frame the layer's contents.

The script checks that the host shows the frame where the view is, the right
way up: green at the left, red at the right, blue at the top right, white
around it. It prints one PASS/FAIL line per check (12) and exits nonzero on
any failure. It leaves the host's screen in `out/ios-opengles.png`, and
exits the app with a tap on the view.

Passes 12/12:
- in an arm64 VM (Arch Linux ARM, Mesa 26.2 llvmpipe, OpenGL ES 3.2);
- on Android 13 (Galaxy Note10 Lite, Mali-G72, OpenGL ES 3.2). There the
  host programs ran from Termux as the APK runs them, with pocket-host built
  by the NDK.

Not obvious:

- **The GL functions are trampolines** (`src/gles-functions.c`, generated by
  `gen-gles-functions.py` from Khronos's headers). Each one jumps to the
  host's function, looked up in libGLESv2, then libGLESv1_CM, then with
  `eglGetProcAddress`. Calls go straight into the host's code, as Darling's
  ELF wrappers do: Darling keeps the host's thread pointer, so the driver
  finds its current context.
- **Apple's arm64 ABI packs stack arguments by their size; AAPCS64 gives
  each 8 bytes.** The functions whose stack arguments land in different
  places get a C wrapper instead (`glBlitFramebuffer`, `glTexSubImage3D` and
  ten others).
- **iOS names the host lacks** fall back to the core function (OES and EXT
  suffixes), to an alias (`glDiscardFramebufferEXT`), to an implementation
  (`glResolveMultisampleFramebufferAPPLE` as a blit), or to a function that
  does nothing, with a log line.
- **Apps that present from their own loop** (SDL's) seldom let the run loop
  wait, which is when UIKit draws. So presenting draws the window at once.
